# Lumi frontend

The web app of Lumi, built with [Next.js](https://nextjs.org/) and React. It serves the public chat at `/`, the `/widget` page that the [widget](../widget/README.md)'s launcher opens in an iframe, the onboarding wizard at `/setup`, the admin interface at `/admin`, and the widget script at `/scripts/lumi-widget.bundle.umd.js`. Conversations stream from the backend's agents API; business data, settings and admin operations go through its GraphQL API ([backend](../backend/README.md)). Chat and request types shared with the backend live in [`@lumi/shared-contracts`](../packages/shared-contracts/README.md).

How the app is used and configured in an installation is in the documentation: [The admin interface](https://docs.lumi.nieve.ai/using-lumi/admin-interface), [Configuration](https://docs.lumi.nieve.ai/configuration), [Admin access](https://docs.lumi.nieve.ai/configuration/admin-access) and the [Self-hosting settings](https://docs.lumi.nieve.ai/self-hosting#settings). This README is for working on the app.

## Local development

Set up the checkout and the local services first, as [Getting started](https://docs.lumi.nieve.ai/getting-started) describes. Then copy [`.env.example`](.env.example) to `.env.local` and run the development server:

```bash
pnpm dev
```

The example settings use the local services of `pnpm start:local-dev`, whose proxy serves the app with the same routes as a container installation. Open [http://localhost:8080](http://localhost:8080) for the public chat and [/admin](http://localhost:8080/admin) for the admin interface. The dev server also answers on port 3000, but there the chat can't reach `/agents`, which only the proxy serves.

The chat talks to the agents API. Locally, run `pnpm -C backend dev:agents`, `pnpm -C backend dev:apollo` for GraphQL and `pnpm -C backend dev:tasks` for PDF resumes. With the example settings the browser calls `/agents` through the proxy, and the server reaches GraphQL and `/pdf` through it (`API_ENDPOINT=http://localhost:8080`) and the agents API directly (`AGENTS_INTERNAL_ENDPOINT`). Without them, `NEXT_PUBLIC_AGENTS_ENDPOINT` defaults to `http://localhost:4200/agents`. It is built into the browser code, so a build for a backend on the [AWS Lambda adapters](../backend/README.md#aws-lambda-adapters), such as one on Vercel, must set it to the streaming agents API's endpoint (the backend stack's `AgentsApiEndpoint` output).

## Layout

- `src/app`: routes. The public chat is `src/app/chat/[lang]/page.tsx`, the iframe page `src/app/widget`, the onboarding wizard `src/app/setup` and the admin interface `src/app/admin`.
- `src/components`: reusable UI; `src/components/ui` holds the base components.
- `src/lib`: client and server helpers, including admin access (`src/lib/auth`) and the GraphQL clients.
- `src/generated`: GraphQL types generated by `pnpm codegen`. Never edit them by hand; follow [backend/AGENTS.md](../backend/AGENTS.md#graphql-codegen).
- `public/scripts`: the widget bundle, copied there by the widget's `build:full`.

Conventions for people and coding agents are in [AGENTS.md](AGENTS.md).

## Business settings

The public chat and the `/widget` page show the business settings stored in the database: the business's and the assistant's names, the assistant's picture, the logo, primary colour, default language, contact links, and the chat's greeting and starters. Until the onboarding wizard has saved them, every page but `/widget` redirects to `/setup`. The chat pages are prerendered and refreshed when the settings are saved, and `/api/business` serves the widget its part of them. The server-only agent guidance never reaches the browser outside the admin Settings page. The settings and their checks are in `@lumi/shared-contracts/business`; what each one does is in [Configuration](https://docs.lumi.nieve.ai/configuration).

## How admin sign-in works

`/admin` requires an admin session; visitors, the public chat, the widget, PDF resumes and media need none. `ADMIN_AUTH_PROVIDER` picks one sign-in mode per installation: `local` (email and password accounts stored by the backend) or `workspace` (Google Workspace accounts in the admin Google Group). Unset or any other value leaves admin sign-in unavailable, and missing settings of the chosen mode deny access rather than open it. Setting it up, its variables and the Google setup are in [Admin access](https://docs.lumi.nieve.ai/configuration/admin-access).

In the code:

- Sign-in uses [NextAuth.js](https://next-auth.js.org/) v4 with only the mode's provider. The session is an encrypted, HttpOnly JWT cookie that ends 12 hours after sign-in (`src/lib/auth/session.ts`): NextAuth renews the cookie when the session is read, so the sign-in time kept in the token enforces the limit. The token keeps the provider (`google` or `local`), the account (`sub`), email, name and sign-in time, and in `local` mode when the account's password was last set (`passwordChangedAt`). A session from the other mode grants nothing, so switching `ADMIN_AUTH_PROVIDER` signs everyone out. Sessions from before the modes existed count as Google ones.
- `requireAdminAccess()` (`src/lib/auth/admin.ts`) checks access again before every admin page read and server action, and `adminRouteAccess()` / `adminRouteError()` in admin route handlers (401 without a session, 403 without admin access, 503 when it can't be checked). The proxy (`src/proxy.ts`) only sends admin page requests without a valid session of the current mode to the sign-in page. Admin GraphQL calls go through `getAdminClient()` (`src/lib/adminApiClient.ts`), which checks admin access before using `API_KEY`. Agents API admin calls go through `fetchAgentsAdmin` (`src/lib/agentsAdmin.ts`) after their caller checks admin access. Public callers use `getClient()` directly.
- `local`: the sign-in form sends the email and password to NextAuth's Credentials provider (`id: "local"`), which asks the API's `verifyAdminCredentials` with the client IP (the first `X-Forwarded-For` entry, else `X-Real-IP`). Passwords only travel as GraphQL variables and are never logged. Every privileged request looks the session's account up (`adminAccount`) without a cache, so a removed account or a changed password applies at once on every server instance: a session whose `passwordChangedAt` differs from the account's must sign in again. An account with a temporary password is sent to `/auth/change-password` before any admin page; server actions redirect there and admin route handlers answer 403. Password rules are in `@lumi/shared-contracts/adminAccounts`.
- `workspace`: Google sign-in uses the scopes `openid email profile`, PKCE and state, and requires a verified email and an `hd` claim in `ADMIN_ALLOWED_DOMAINS`. Membership of the Google account ID in the admin group is checked with the Admin SDK Directory API (`members.hasMember`) at sign-in and again by `requireAdminAccess()`, cached for 5 minutes per server instance when positive and 30 seconds when negative. A failed or timed-out check denies access.

## Langfuse

The admin conversation page links to the conversation's Langfuse session when `LANGFUSE_PROJECT_ID` is set (the backend traces each conversation with its thread id as the session id). The admin editor's "Help improve" completion is traced as `improve-text` (`src/lib/tracing.ts`, registered from `src/instrumentation.ts`) when both Langfuse keys are set; without them it runs untraced. The variables are in [`.env.example`](.env.example), and setting it up for an installation is in [Tracing with Langfuse](https://docs.lumi.nieve.ai/self-hosting/operations#tracing-with-langfuse).
